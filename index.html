Chapter 01

What is Active Directory?

Microsoft's directory service that stores information about objects on a network and makes this information available to users and administrators.

🔒

Identity & Access

Centralized identity management for users, computers, and services across the enterprise network.

📄

Directory Service

Hierarchical database of network resources following LDAP (Lightweight Directory Access Protocol) standards.

⚙

Policy Management

Group Policy Objects (GPOs) enable centralized configuration of computers and user settings.

🔗

Authentication

Kerberos and NTLM protocols provide secure Single Sign-On (SSO) authentication.

Azure Active Directory rebranded to Microsoft Entra ID — cloud-native identity platform at scale.

First new AD DS schema update since 2016. Hotpatching for AD servers, dMSA (delegated Managed Service Accounts), 32-bit DNT upgrade, LDAP channel binding enforced by default, SMB over QUIC, improved NTDS performance.

💡

Core AD Components

  • Forest Top-level security and administrative boundary
  • Domain Administrative unit containing users, computers, and groups
  • OU Organizational Unit — logical container for policy application
  • DC Domain Controller — server hosting the AD database (NTDS.dit)
  • GC Global Catalog — partial replica of all objects in the forest
  • FSMO Flexible Single Master Operations — 5 special DC roles
  • GPO Group Policy Object — configuration settings for users/computers
  • Schema Defines all object classes and attributes in the directory

Spotlight: Microsoft Entra Domain Services

What is Entra Domain Services?

Microsoft Entra Domain Services (Entra DS) is a fully managed, cloud-hosted domain service that provides classic AD DS capabilities — LDAP, Kerberos, NTLM, Group Policy, and domain join — without you having to deploy, patch, back up, or manage any domain controllers.

It runs as a managed service in Azure. Microsoft provisions two domain controllers in your chosen Azure region (and a replica set in another region if you add it), keeps them patched, monitored, and highly available.

Identities and groups are one-way synchronized from Microsoft Entra ID into the managed domain, so users keep their existing cloud credentials.

Solution — when to use it

✅
Lift-and-shift legacy apps to Azure that require Kerberos, LDAP binds, or NTLM — e.g., SQL Server, line-of-business apps, SAP, file servers.
✅
Domain-join Azure VMs (Windows or Linux with SSSD) without needing a VPN back to on-prem DCs.
✅
Azure Virtual Desktop / Azure Files deployments that need Kerberos authentication for SMB shares.
✅
No on-prem footprint required — small/startup orgs that want AD DS behavior entirely in the cloud.
✅
Reduce operational overhead — no DC patching, no backups to manage, no FSMO worries.

Implementation — Cloud-Only

☁ Cloud-only Entra DS

Users live in Microsoft Entra ID only (no on-prem AD). Entra ID is the source of truth; Entra DS is the managed classic-protocol domain.

Prepare the tenantHave a Microsoft Entra ID tenant with user accounts. If users originate as cloud-only, they must reset their password after Entra DS is enabled so the NTLM/Kerberos hashes are generated.
Create an Azure VNet & subnetDedicated VNet with a subnet (e.g., 10.0.1.0/24) that will host the managed domain controllers. Avoid overlapping ranges.
Provision Entra Domain ServicesAzure Portal → Create Microsoft Entra Domain Services. Choose: managed domain DNS name (e.g., contoso.onmicrosoft.com or a custom aaddscontoso.com), SKU, region, VNet/subnet. Provisioning takes ~30–60 min.
Update VNet DNSPoint VNet DNS settings to the two IPs assigned to the managed domain. All VMs in that VNet now use the managed domain for name resolution.
Enable password syncUsers must change their password at least once after enablement for Kerberos/NTLM credentials to be generated and synced into Entra DS.
Domain-join workloadsJoin Azure VMs, App Service Environments, Azure Files, or AVD host pools using the managed domain DNS name. Standard djoin / Windows "Join a domain" works.
Optional: Secure LDAPEnable LDAPS using a certificate from an internal CA or public CA. Required for most line-of-business apps that need secure LDAP binds.
Optional: Add replica setFor HA / DR across regions, add an Entra DS replica set in a second Azure region.
Azure CLI — Provision cloud-only Entra DS
# Login and set subscription
az login
az account set --subscription "<SubId>"

# Create resource group + VNet + subnet
az group create --name rg-eds --location southeastasia
az network vnet create --resource-group rg-eds \
  --name vnet-eds --address-prefix 10.0.0.0/16 \
  --subnet-name snet-eds --subnet-prefix 10.0.1.0/24

# Register the resource provider (first-time only)
az provider register -n Microsoft.AAD

# Create the managed domain (the portal-equivalent step).
# The 'az ad ds' commands require the aad-ds CLI extension.
az extension add --name aad-ds

az ad ds create --resource-group rg-eds \
  --name aaddscontoso.com --location southeastasia \
  --sku Standard \
  --replica-sets '[{"location":"southeastasia","subnetId":"/subscriptions/<SubId>/resourceGroups/rg-eds/providers/Microsoft.Network/virtualNetworks/vnet-eds/subnets/snet-eds"}]'

Implementation — Hybrid

🔀 Hybrid: on-prem AD DS + Entra ID + Entra DS

On-prem AD DS is the source of truth. Microsoft Entra Connect syncs users/groups and password hashes to Entra ID, which in turn feeds Entra DS.

Confirm Entra Connect sync methodUse Password Hash Sync (PHS). Pass-Through Auth alone is not sufficient — Entra DS needs the legacy hash to generate Kerberos/NTLM credentials.
Verify directory syncConfirm users and groups appear in Entra ID with correct UPN and SIDs. Resolve any sync errors before provisioning Entra DS.
Decide namespace strategyPick an Entra DS DNS name distinct from your on-prem AD (e.g., on-prem is corp.contoso.com, Entra DS is aadds.contoso.com) — avoids namespace collision and lets you build an outbound forest trust from on-prem AD if needed.
Provision Entra DS in a dedicated VNetSame as cloud-only. Peer this VNet with your hub / on-prem connectivity (ExpressRoute or VPN) so hybrid clients can reach it.
Password reset waveOn-prem users who existed before PHS was enabled must change their password once for NTLM/Kerberos hashes to flow through to Entra DS.
Optional one-way trust from on-premCreate a one-way forest trust from on-prem AD DS → Entra DS. On-prem users can access resources joined to Entra DS without existing in it. Entra DS cannot write back to on-prem.
Route workloads appropriatelyLift-and-shift apps in Azure join aadds.contoso.com. On-prem workloads keep using corp.contoso.com. Both sets of users authenticate seamlessly.
Monitor & costEntra DS billing is per-hour per instance. Monitor via Azure Monitor + Entra DS health blade. Entra Connect and on-prem AD continue to be your responsibility.
💡

Gotchas to remember

  • No schema extensions — apps that require custom AD schema (older Exchange, some LoB apps) will not run on Entra DS.
  • LDAP is read-only — apps that write to the directory via LDAP won't work.
  • Password reset required for existing cloud-only users and on-prem users synced before PHS enablement.
  • No Enterprise/Domain Admin — you get AAD DC Administrators, a scoped admin group. You cannot RDP into the managed DCs.
  • Trusts are one-way outbound from on-prem AD to Entra DS. Entra DS cannot host a child domain of on-prem AD.
  • Pricing: Entra DS Standard starts around $0.10/hr (~$73/mo). Enterprise and Premium SKUs cost more but support more objects and features.

How to Upgrade Functional Level

Raising the Domain Functional Level (DFL) or Forest Functional Level (FFL) unlocks newer AD features but is a one-time directional change. Plan and validate before raising.

⚠️

Prerequisites

  • All DCs in the domain (for DFL) or forest (for FFL) must run the target OS or newer.
  • Raise the DFL first on every domain, then the FFL for the forest.
  • Replication must be healthy. Run repadmin /replsummary before raising.
  • Perform a System State backup of all DCs beforehand.
  • Verify no legacy DCs (NT4, 2003, 2008/R2) exist — use Get-ADDomainController -Filter *.
🔓

Rollback Rules

  • DFL/FFL raises are generally one-way.
  • Rollback is possible only from WS 2008 R2 or higher back down — and only if AD Recycle Bin and other features depending on that level have not been enabled.
  • You cannot lower below WS 2008 R2 once raised.
  • Once a feature like AD Recycle Bin is enabled, the forest FL becomes locked.
💡

Best Practices

  • Wait until all DCs are stable on the new OS for at least a few weeks before raising.
  • Raise levels during a maintenance window.
  • Document the pre/post state (schema version, DFL, FFL) in a change record.
  • After raising to WS 2025 FL, you can no longer add DCs running older OS versions.
PowerShell — Check Current Functional Levels 
# Check current Domain Functional Level
Get-ADDomain | Select-Object DNSRoot, DomainMode

# Check current Forest Functional Level
Get-ADForest | Select-Object Name, ForestMode

# Check OS version of every Domain Controller
Get-ADDomainController -Filter * |
  Select-Object Name, OperatingSystem, OperatingSystemVersion, Site |
  Sort-Object Name

# Verify replication health
repadmin /replsummary
repadmin /showrepl * /csv | ConvertFrom-Csv | Where-Object {$_.'Number of Failures' -gt 0}
PowerShell — Raise Domain & Forest Functional Level 
# Available DomainMode / ForestMode values (WindowsThreshold = WS 2016):
#   Windows2008R2Domain    / Windows2008R2Forest
#   Windows2012Domain      / Windows2012Forest
#   Windows2012R2Domain    / Windows2012R2Forest
#   WindowsThreshold       / WindowsThreshold       (WS 2016)
#   Windows2025Domain      / Windows2025Forest      (WS 2025)

# Step 1: Raise Domain Functional Level (do this for EACH domain)
Set-ADDomainMode `
  -Identity "contoso.com" `
  -DomainMode Windows2025Domain `
  -Confirm:$false

# Step 2: Raise Forest Functional Level (only after ALL domains are at target DFL)
Set-ADForestMode `
  -Identity "contoso.com" `
  -ForestMode Windows2025Forest `
  -Confirm:$false

# Step 3: Verify the change
Get-ADDomain | Select-Object DNSRoot, DomainMode
Get-ADForest | Select-Object Name, ForestMode

# Step 4 (optional): Enable features unlocked by the new FL
# AD Recycle Bin requires Forest FL 2008 R2+ and is a ONE-WAY enablement
Enable-ADOptionalFeature `
  -Identity "Recycle Bin Feature" `
  -Scope ForestOrConfigurationSet `
  -Target "contoso.com" `
  -Confirm:$false

02

Infrastructure Preparation

💻

Server Hardware / VMs

Minimum: 2 vCPU, 4 GB RAM, 60 GB disk per DC. Recommended: 4 vCPU, 8 GB RAM, 100 GB.

📡

Network Configuration

Static IP for all DCs. Configure DNS to point to itself (first DC) or other DCs. Ensure ports open: TCP/UDP 88, 389, 636, 3268, 3269, 445, 49152-65535.

📄

OS Installation & Updates

Install Windows Server, apply all updates. Rename server before promotion. Join to workgroup (not another domain yet).

03

AD DS Deployment

PowerShell — Install AD DS Role & Promote First DC 
# Step 1: Install AD DS role
Install-WindowsFeature -Name AD-Domain-Services -IncludeManagementTools

# Step 2: Import ADDSDeployment module
Import-Module ADDSDeployment

# Step 3: Promote to Domain Controller (New Forest)
Install-ADDSForest `
  -DomainName "contoso.com" `
  -DomainNetbiosName "CONTOSO" `
  -DomainMode "WinThreshold" `
  -ForestMode "WinThreshold" `
  -DatabasePath "C:\Windows\NTDS" `
  -LogPath "C:\Windows\NTDS" `
  -SysvolPath "C:\Windows\SYSVOL" `
  -InstallDns:$true `
  -SafeModeAdministratorPassword (ConvertTo-SecureString `
    "P@ssw0rd123!" -AsPlainText -Force) `
  -Force:$true

# Server will automatically restart after promotion
PowerShell — Add Additional Domain Controller 
# Install AD DS role on second server
Install-WindowsFeature -Name AD-Domain-Services -IncludeManagementTools

# Promote as additional DC in existing domain
Install-ADDSDomainController `
  -DomainName "contoso.com" `
  -InstallDns:$true `
  -Credential (Get-Credential "CONTOSO\Administrator") `
  -SafeModeAdministratorPassword (ConvertTo-SecureString `
    "P@ssw0rd123!" -AsPlainText -Force) `
  -Force:$true

Controls all changes to the AD schema. Only one per forest. Keep on a secure, well-maintained DC.

🏠 Domain Naming Master

Controls addition/removal of domains in the forest. Must be a Global Catalog server.

Domain-wide (1 per domain)

📄 RID Master

Allocates pools of relative identifiers (RIDs) to DCs, ensuring unique SIDs for all objects.

📅 PDC Emulator

Password changes, account lockouts, time synchronization, legacy client support. Most sensitive role.

🔗 Infrastructure Master

Updates cross-domain group-to-user references. Should NOT be on a GC server (unless all DCs are GCs).

Chapter 08

AD Attacks & Defense

Common attack techniques against Active Directory — how they work, how to detect them, and how to defend.

Credential Theft

Kerberoasting

High Severity MITRE T1558.003

🚨 How it works

  1. Attacker with any valid domain user requests a Kerberos service ticket (TGS) for an account with an SPN (Request-SPNTicket, Rubeus).
  2. The TGS is encrypted with the service account's NTLM/RC4 password hash.
  3. Attacker extracts the ticket and cracks it offline with hashcat (mode 13100) — weak passwords fall in minutes.
  4. Service account credentials are now compromised, often with high privileges.

🔍 Detection

  • Event ID 4769 with Encryption Type 0x17 (RC4) — legitimate modern traffic uses AES.
  • Unusual volume of TGS requests from a single account for many SPNs.
  • Microsoft Defender for Identity: "Suspected Kerberoasting attack" alert.

🛡️ Hardening

  • Use group Managed Service Accounts (gMSA) or dMSA (WS 2025) — passwords are machine-managed and 120 chars.
  • Force AES-only tickets: msDS-SupportedEncryptionTypes = 0x18.
  • Minimum 25-char password on service accounts that must stay as traditional users.
  • Add Protected Users group membership — blocks RC4 and NTLM.
PowerShell — Find SPN-enabled accounts (hunt your own) 
Get-ADUser -Filter {ServicePrincipalName -like "*"} `
  -Properties ServicePrincipalName, PasswordLastSet, msDS-SupportedEncryptionTypes |
  Select-Object SamAccountName, ServicePrincipalName, PasswordLastSet, msDS-SupportedEncryptionTypes
Privilege Escalation

Golden Ticket

Critical MITRE T1558.001

🚨 How it works

  1. Attacker compromises the krbtgt account hash (via DCSync, DC compromise, old backup).
  2. With the krbtgt hash + domain SID, attacker forges a TGT for any user, including Domain Admins.
  3. Forged TGT is valid for up to 10 years by default — persistent domain-wide access.
  4. Bypasses MFA, password changes, and account disables — only krbtgt rotation invalidates it.

🔍 Detection

  • Event ID 4769 for accounts that never requested a TGS before.
  • TGT lifetime longer than policy (default max 10h).
  • Event ID 4624 logons without a preceding 4768 (AS-REQ).
  • Defender for Identity: "Suspected Golden Ticket usage" alert.

🛡️ Hardening

  • Rotate krbtgt password twice (with 10h gap) after any Tier-0 incident — mandatory annually.
  • Protect DCs: no browsing, no email, no admin logon from workstations (PAW model).
  • Tier the admin model (Tier 0/1/2). Never cache DA credentials on Tier 2 hosts.
  • Enable Credential Guard on Tier 0.
Credential Theft

DCSync

Critical MITRE T1003.006

🚨 How it works

  1. Attacker abuses the DS-Replication-Get-Changes and DS-Replication-Get-Changes-All rights.
  2. Impersonates a DC and requests replication of password hashes via the Directory Replication Service Remote Protocol (MS-DRSR).
  3. Dumps all hashes including krbtgt — feeds directly into Golden Ticket attacks.
  4. Does not require code execution on a DC.

🔍 Detection

  • Event ID 4662 on DCs with GUIDs 1131f6aa-... (Get-Changes) and 1131f6ad-... (Get-Changes-All) from non-DC principals.
  • SACL on the domain object; filter on principal != DC computer account.
  • Defender for Identity: "Suspected DCSync attack (replication of directory services)" alert.

🛡️ Hardening

  • Audit who holds the DS-Replication-* rights — should only be Domain Controllers, Enterprise Domain Controllers, Administrators.
  • Regularly review delegations on the domain root.
  • Protect admin accounts with MFA and Privileged Access Workstations.
Lateral Movement

Pass-the-Hash / Pass-the-Ticket

High Severity MITRE T1550.002 / T1550.003

🚨 How it works

  1. Attacker dumps NTLM hashes or Kerberos tickets from LSASS (mimikatz, lsassy).
  2. Reuses the hash/ticket to authenticate as the user — no plaintext password needed.
  3. Moves laterally between hosts sharing local admin passwords or cached credentials.

🔍 Detection

  • Event ID 4624 Logon Type 3 (network) + Logon Process NtLmSsp on multiple hosts quickly.
  • Event ID 4648 explicit-credential logons from unusual sources.
  • Defender for Identity: "Suspected Overpass-the-Hash attack".

🛡️ Hardening

  • Deploy Windows LAPS — unique local admin password per machine.
  • Enable Credential Guard (Windows 10/11 + Server 2016+).
  • Disable WDigest cleartext caching.
  • Disable NTLM where possible; audit with Event ID 8004.
  • Tier 0 admins go in Protected Users group.
Credential Theft

AS-REP Roasting

Medium Severity MITRE T1558.004

🚨 How it works

  1. Attacker targets accounts with "Do not require Kerberos preauthentication" enabled.
  2. Sends an AS-REQ without preauth — DC returns an AS-REP encrypted with the user's password hash.
  3. Attacker cracks the AS-REP offline (hashcat mode 18200). Succeeds without any prior credentials.

🔍 Detection

  • Event ID 4768 with pre-auth type = 0.
  • Volume spike of unauthenticated AS-REQs.
  • Hunt: find accounts with DONT_REQ_PREAUTH flag set.

🛡️ Hardening

  • Clear the DONT_REQ_PREAUTH flag on all accounts (usually leftover from legacy apps).
  • If required, enforce 25+ char passwords on those accounts.
PowerShell — Find accounts without Kerberos preauth 
Get-ADUser -Filter 'useraccountcontrol -band 4194304' `
  -Properties SamAccountName, PasswordLastSet, Enabled |
  Where-Object Enabled -eq $true

Defense-in-Depth Stack

Prevent
  • Tiered admin model + PAWs
  • Protected Users group
  • Credential Guard + LAPS
  • Disable NTLMv1, WDigest
  • LDAP channel binding
Detect
  • Microsoft Defender for Identity
  • SIEM: Sentinel, Splunk, Elastic
  • Honey accounts + HoneyHashes
  • SACL on sensitive AD objects
  • Audit policy: Kerberos, Account Management
Respond
  • krbtgt rotation playbook (x2)
  • Isolate compromised DCs
  • Reset Tier 0 credentials
  • Authoritative restore procedure
  • Forensic triage: KAPE, Velociraptor

Chapter 12

FAQ & Resources

Frequently asked questions about Active Directory implementation and management.

How many Domain Controllers should I deploy? +

At minimum, deploy 2 DCs per domain for redundancy. A general guideline is 1 DC per 1,000-2,000 users, plus at least 1 DC per site/location. For branch offices with fewer than 50 users and limited physical security, consider a Read-Only Domain Controller (RODC) to reduce risk.

Should I use a .local domain name or a routable DNS suffix? +

Use a routable DNS suffix (e.g., corp.contoso.com or contoso.local is no longer recommended). Microsoft recommends using a subdomain of your public domain (e.g., corp.contoso.com) or a completely separate routable domain. The .local suffix causes issues with mDNS/Bonjour, macOS clients, and hybrid Azure AD scenarios.

What's the difference between AD DS and Azure AD (Entra ID)? +

AD DS is the traditional on-premises directory service using Kerberos/NTLM, LDAP, Group Policy, and OUs. Microsoft Entra ID is a cloud-based identity platform using OAuth 2.0, OIDC, SAML 2.0 — built for internet-scale and SaaS applications. They are complementary, not interchangeable. Most enterprises use hybrid identity: AD DS on-premises synced to Entra ID via Microsoft Entra Connect.

How do I migrate from Windows Server 2012 R2 DCs to 2022? +

Use the "introduce new, transfer roles, decommission old" method: (1) Add new WS2022 DCs to the existing domain, (2) Let replication sync fully, (3) Transfer FSMO roles to new DCs using Move-ADDirectoryServerOperationMasterRole, (4) Raise Domain/Forest Functional Level after removing all old DCs, (5) Decommission old DCs using dcpromo /forceremoval and clean up metadata.

Can I run Active Directory on virtual machines? +

Yes — this is the standard approach today. Key considerations: (1) Use VM Generation ID aware hypervisors (Hyper-V, VMware 5.5+), (2) Never snapshot/restore DCs — it causes USN rollback, (3) Don't co-locate all DC VMs on a single physical host (anti-affinity rules), (4) Ensure DCs have sufficient dedicated resources and are not overprovisioned. The AD Recycle Bin is a better option than VM snapshots.

Is LDAP channel binding / LDAP signing mandatory? +

Yes — as of March 2024, Microsoft enforces LDAP channel binding and LDAP signing by default on all supported DCs via cumulative updates. On Windows Server 2025 this is enforced out of the box. Legacy apps using unencrypted simple binds will break. Audit first using Event IDs 3039 (unsigned LDAP), 3040 (unprotected simple bind), and 3041 (channel binding). Remediate by enabling LDAPS (port 636) or STARTTLS before enforcement.

Do I still need to download LAPS separately? +

No. Windows LAPS is now built into Windows 10/11 and Windows Server 2019+ (via April 2023 updates). The legacy "Microsoft LAPS" MSI is deprecated. The new Windows LAPS supports both AD and Entra ID as the backend, policy via GPO or Intune, and includes automatic password rotation after use. Enable with GPO under Computer Configuration → Policies → Administrative Templates → System → LAPS.

How do I migrate from Windows Server 2016/2019 to 2025? +

Follow the same pattern as other DC upgrades: (1) Verify forest/domain functional level is at least WS 2016, (2) Add new Windows Server 2025 DCs via Install-ADDSDomainController, (3) Wait for full replication, verify with repadmin /replsummary, (4) Transfer FSMO roles with Move-ADDirectoryServerOperationMasterRole, (5) Demote old DCs with Uninstall-ADDSDomainController, (6) Raise functional level to WS 2025 to unlock dMSA, 32-bit DNT, and PKINIT algorithm agility. Warning: Once raised to WS 2025 FL, you cannot add DCs running older OS versions.

What are dMSAs (delegated Managed Service Accounts)? +

Introduced in Windows Server 2025, delegated Managed Service Accounts are the successor to traditional service accounts and gMSAs. They defend against Kerberoasting by binding the account to specific machine identities — only designated machines can authenticate. Passwords are machine-generated, auto-rotated, and never known to humans. Migrate existing service accounts with Start-ADServiceAccountMigration.

What is the AGDLP naming convention? +

AGDLP = Accounts → Global groups → Domain Local groups → Permissions. Place user accounts in Global security groups (organized by role/department). Nest Global groups into Domain Local groups. Assign resource permissions to Domain Local groups. This allows cross-domain membership while keeping permission management simple and scalable.
